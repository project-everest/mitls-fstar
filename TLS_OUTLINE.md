We have an implementation of a TLS-1.3 Client in Pulse & F*. The proof of
correctness is in progress, but it is messy and incomplete.

I want to revise the proof following the methodology developed in the
calc_sample directory. Read CALC_DESIGN_AND_IMPL.md for details. 

Let's make a plan to apply the CALC methodology to the TLS-1.3 Client
implementation.

The key steps involve:

* Specifying the wire format of TLS messages as pure F* datatypes (call the M
  for the message types) and spec functions to parse/serialize from bytes to M
  and back.

* Defining the low-level datatypes L that correspond to M. These datatypes L
  should be extractable to C, so they should use machine integer types rather
  than unbounded integers. For any variable-length type (e.g., fields
  representing keys etc.) they should use Pulse `Array.array U8.t` rather than
  lists or sequences.

* Writing an interface file for concrete parsers and serializers that convert
  from an input `array U8.t` to L and back. The specifications of these
  functions should relate their behavior to the pure spec functions that convert
  from bytes to M and back.

* The actual parsers and serializers will be implemented directly in C and we
  will link the rest of our verified code against these C implementations,
  assuming they satisfy the specification in the interface. (Later, we will
  replace this layer with verified code generated by EverParse).

* Then, define a high-level state transition relation for TLS-1.3 clients, based
  as a the transitive closure of a single step relation that takes a state, an
  input message M, and produces a new state and an output message. This will be
  defined in terms of the pure M datatypes and pure functions that manipulate
  them. See the Calc.Log and Calc.Spec style.

* The spec will involve the use of cryptographic functions, which we will take
  from HACL*/dist, again with interfaces that describe their behavior in terms
  of abstract pure F* functions. The spec will also rely on cerificate
  validation, which we will also specify in terms of pure F* functions, but
  reuse the implementation in C from openssl.

* Once we have our purely functional spec in the style of Calc.Log and its
  log_consistent relation relating wire format, to pure M messages, to state
  transitions, and finally to application-level messages, we can relate our
  concrete implementation to the spec.

* Follow the style of the calc sample where the top-level interface is driven by
  a process request function that takes an input message, updates the state, and
  produces an output message. We can separately write a top-level driver that
  calls into this process_request function by sending/receiving bytes from the
  network.

* Note, we are not implementing a full TLS-1.3 profile: we are only supporting a
  single ciphersuite (chacha/poly with x25519), and 1-RTT basic handshakes.

* At the end of the process, we should be able to interoperate our client with
  an existing openssl TLS server.
