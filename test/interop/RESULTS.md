# ATLAS interop: top-100 public HTTPS sites

Generated by `test/interop/sweep.sh` (ATLAS) and `test/interop/oracle.sh`
(reference upper bound).  Catalog: `test/interop/top100.tsv` -- the first 100
entries of the Tranco top-1m that negotiate TLS 1.3, in rank order, plus
`nytimes.com` at rank 101.

## ATLAS's offer

ATLAS currently offers exactly one group, one cipher suite and two signature
schemes:

| Parameter | Value |
|---|---|
| Group | `X25519` |
| Cipher suite | `TLS_CHACHA20_POLY1305_SHA256` (`0x1303`) |
| Signature schemes | `rsa_pss_rsae_sha256` (`0x0804`), `ecdsa_secp256r1_sha256` (`0x0403`) |

The **oracle** column is OpenSSL constrained to *exactly* that offer, with
hostname verification on.  A host that the oracle cannot reach is out of reach
of any client with ATLAS's crypto -- it is not an ATLAS defect.

Empirical note: **zero** of the 101 sites serve an Ed25519 certificate.  The
real-world signature schemes are RSA-PSS and ECDSA P-256.

## Bugs found and fixed

1. **Certificate chain building.** `X509_STORE_CTX_init` was passed `NULL` for
   the untrusted stack, discarding the server's intermediates.  Public CAs
   issue end-entity certificates from intermediates, so no real site could
   build a path to an anchor.  The in-tree test only passed because its leaf is
   issued directly by the test root.  Fixed by plumbing the server's chain
   through to the oracle (`set_peer_certificate_chain`), loading *every* PEM
   certificate as an anchor, and setting `X509_V_FLAG_PARTIAL_CHAIN`.
2. **Coalesced-record drain.** `drain_pending` was only reachable from the
   record path.  A coalesced flight cannot be drained in one go -- e.g.
   `CertificateVerify` is illegal until `LocalValidateCertificate` has run --
   so the remaining messages sat in the pending buffer while the driver blocked
   on a socket read the peer would never satisfy.  Fixed by draining after
   every successful local event (`BufferedNetwork.drain_pending_internal`).
3. **Leaf DER capacity.** The public-key payload capacity was 4096 bytes; real
   leaves with large SAN lists exceed it (googleapis.com 6840 B,
   googleusercontent.com 6779 B).  Raised to 16384 in `Bounds`, the driver, the
   engine interface and the C header.
4. **ECDSA P-256 not offered.** Adding `ecdsa_secp256r1_sha256` to the default
   offer raised the achievable ceiling from 80 to 83 and unblocked several
   sites that serve only ECDSA credentials.

A fifth defect was in the harness, not in ATLAS: the per-host anchor extractor
fetched chains *unconstrained*, so dual-credential servers returned a chain
anchored at a different root than the one ATLAS actually receives.

## Remaining failures

### Real ATLAS gap: cross-record handshake fragmentation (6 sites)

facebook.com, instagram.com, fbcdn.net, whatsapp.com, whatsapp.net, wa.me.

TLS 1.3 permits a single handshake message to span several records.  Meta
serves its server flight in three protected records (1000 / 2161 / ~100 bytes
of plaintext); `EncryptedExtensions` is 6 bytes and `Certificate` starts at
offset 6 and runs past the end of the first record.

`legal_protected_handshake_step`'s head branch requires
`protected_handshake_buffer_empty`, so the next record cannot be joined to the
leftover -- ATLAS reports `PROT_ERROR` and fails the step.  Closing this
requires the head step to accept `leftover ++ record_plaintext` as its
fragment, which touches the receive legality relation, the `ProtectedWire*`
normal-form modules and the sent/received pairing argument.  It is tracked
separately as a spec-level change, not a bug fix.

### Beyond ATLAS's offer (15 sites)

| Missing capability | Sites |
|---|---|
| AES-128-GCM (no ChaCha20) | amazon.com, azure.com, cloud.microsoft, skype.com, windows.com, windows.net, trbcdn.net (also needs P-384) |
| AES-128-GCM **and** secp256r1 | bing.com, live.com, msn.com, office.com, outlook.com, sharepoint.com, microsoft.com, office365.com |

The oracle fails on all of these too.  Adding `TLS_AES_128_GCM_SHA256` and
`secp256r1` is the single highest-value follow-up: it would lift the ceiling
from 83 to ~99.

### Genuinely unservable at the apex (3 sites)

googlevideo.com and edgekey.net present certificates that do not match the
apex hostname; domaincontrol.com serves a self-signed certificate.  ATLAS
correctly rejects all three, as does the oracle.

### Diagnostic-only issue

`Common_TCP_read` returns 0 for both EOF and error, and the driver reads 0 as
"no data yet".  A server that RSTs the connection makes ATLAS spin until its
fuel is exhausted (~3 s) instead of reporting "peer closed".  This changes no
verdict; reporting it cleanly would need a new driver outcome.
