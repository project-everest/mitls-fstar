Reading guide and source-of-truth modules

The executable transition function is split by event class: step_local_event, step_handshake_message, step_tls_message, and step_model. Legality is checked separately by legal_*_event. A real state step is the relational wrapper legal_connection_delta, which joins the event, the pure model update, raw-byte deltas, and append-only logs.

Line references point at the current repository layout. The large proof lemmas live outside the audit-facing core in TLS13.ConnectionState.Lemmas.

State inventory

Control states

ConstructorMeaning
ControlNewInitial control state. The nested handshake record starts at HsNotStarted.
ControlHandshaking stageHandshake phase parameterized by the stages below.
ControlApplicationDataHandshake complete; application data, KeyUpdate, tickets, and close_notify are live.
ControlClosingLocal close_notify was sent; peer close_notify is still expected.
ControlClosedPeer close_notify has been accepted.
ControlFailed errorTerminal failure with a TLS error.

Definition: connection_control_state and handshake_stage.

Handshake stages

  1. HsStarted: local start data installed.
  2. HsClientHelloSent: ClientHello stored and transcript-appended.
  3. HsServerHelloReceived: ServerHello stored and transcript-appended.
  4. HsEncryptedExtensionsReceived: encrypted extensions stored.
  5. HsCertificateReceived: certificate chain and leaf DER stored.
  6. HsCertificateValidated: external X509 validation result installed.
  7. HsCertificateVerifyReceived: CertificateVerify and exact signature-input bytes stored.
  8. HsCertificateVerifyVerified: external signature verification result installed.
  9. HsServerFinishedReceived: Finished parsed under server handshake keys.
  10. HsServerFinishedVerified: Finished verify_data checked and transcript-appended.
  11. HsClientFinishedSent: historical handshake stage; the control state moves to ControlApplicationData after client Finished.

Model fields updated by transitions

connection_model_state carries the review-critical state: control phase, configuration, key schedule, handshake artifacts, record read/write state, application log and pending plaintext, key-update response flag, and raw/event logs.

Definitions: key_schedule_state, handshake_state, record_layer_state, application_state, connection_model_state.

Transition details

Each card states the guard used by legal_event, the functional update performed by step_model, and the log/byte obligations added by legal_connection_delta. "Raw sent/received" means the event-specific bytes accepted by event_raw_delta_legal.

application application data, tickets, and KeyUpdate

Source
ControlApplicationData.
Guard
App data send requires client application traffic keys and supported fragment bounds. App data receive and post-handshake messages require server application read keys. KeyUpdate response send with UpdateNotRequested requires app_key_update_response_pending.
Update
Sent application data advances write records by the supported record count and appends to app log. Received application data advances read sequence and appends received bytes to app log. NewSessionTicket is ignored except for record-read advancement. Received KeyUpdate derives and installs new server read keys and may set a pending response flag. Sent KeyUpdate derives and installs new client write keys and clears the pending flag.
Logs/bytes
All network-visible application-state events are protected ApplicationData records. The theorem surface exposes sent seal/read decode/key-schedule projections for protected records.

Application-data and KeyUpdate steps: L651-L745; guards: L968-L980; supported local app-send projection: Client.Types L2834-L2862.

Functional layers preserved by the spec

Single-step transition law

legal_connection_delta st0 delta st1 =
  legal_event st0.cs_model delta.delta_event /\
  step_model st0.cs_model delta.delta_event == Some st1.cs_model /\
  event_raw_delta_legal st0.cs_model delta.delta_event
    delta.delta_raw_sent delta.delta_raw_received /\
  st1.cs_wire_log.raw_sent ==
    st0.cs_wire_log.raw_sent `B.append` delta.delta_raw_sent /\
  st1.cs_wire_log.raw_received ==
    st0.cs_wire_log.raw_received `B.append` delta.delta_raw_received /\
  st1.cs_event_log ==
    st0.cs_event_log `append` [delta.delta_event]

These are intentionally functional views of the same event used by legal_connection_delta.

Raw-to-message replay package

This is the strongest current pure-spec connection from raw wire logs to messages and state evolution.

Raw replay and segmentation definitions: L1688-L1847; top consistency definitions: L2085-L2092.

How this spec relates to the top-level verified client theorem

process_network_bytes

The public extracted network API owns concrete buffers and returns a CT.network_bytes_end_to_end_correct postcondition. That predicate proves the consumed input prefix is either zero, a decode-error witness, or a decoded TLS message/event; successful accepted steps are justified by CS.legal_connection_delta, preserve CT.client_state_correct, preserve CT.client_end_to_end_invariant, and expose raw-record, decoded-message, received-event, received-decode, protected-open/read-key, emitted-output, write-key, and seal projections.

API postcondition: Client.fsti L326-L360; theorem predicate: Client.Types L2791-L2832; step predicate: Client.Types L2450-L2477.

process_local_event

The public extracted local-event API requires only CT.local_input_wf for the concrete payload and returns CT.local_event_end_to_end_correct. The postcondition ties successful local sends to legal spec events, exposes exact emitted network/app prefixes, records X509/signature TCB assumptions through local_auth_tcb_projection, proves supported-profile app-send shape, and preserves the same cumulative client invariants as the network theorem.

API postcondition: Client.fsti L362-L398; theorem predicate: Client.Types L2834-L2862; local step predicate: Client.Types L2684-L2696.

client_state_correct and client_end_to_end_invariant

client_state_correct is the implementation theorem's package of pure reachability and spec-log consistency. client_end_to_end_invariant adds the raw-to-message replay package that connects concrete raw buffers to accepted TLS records/messages, transcript and key-schedule evolution, state-machine events, and application observations.

Theorem packages: Client.Types L2450-L2862; spec consistency roots: ConnectionState L2085-L2092.

Driver and IO history relation

The Pulse driver exposes client_driver_connected d st received sent. This predicate owns the transport channel histories tracked by TLS13.IO.is_channel and relates them to st.cs_wire_log through client_driver_wire_logs_match: sent transport bytes equal the protocol raw-sent log, and received transport bytes split into accepted consumed bytes plus retained buffered read-ahead.

Driver relation: Client.Driver.fsti L21-L50; IO channel history interface: TLS13.IO.fsti.
